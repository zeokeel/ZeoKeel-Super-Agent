## 1. 结论与计数

**Bottom line。** “独立 Go 桌面二进制替代 DSH 宿主插件”这一根本偏离由 design §1.1–1.3 / ADR-1 明确授权（design:65-73、140），在 004 上它带来的损失主要是**能力面**而非形态面：提示词确实实现了“有序 section + 变量插值 + 分离的 Router/Worker/子智能体提示词”，但原型 004 保护的核心资产——**团队三段、逐段覆盖、base-hash 版本化与 “Default updated”、占位符/超长校验、“会话每次请求读最新版本”**——基本缺失；更严重的是人工介入闭环：`ask_user_question` 只能 raise 不能回答，pause/stop/retry 完全不存在，提示词里的“问人”承诺是**通不了的死路**。005 的七页与三问信息架构在代码里成立（且比设计 §6.3 的“消息流主界面”更贴近原型），但“诚实状态”被大量硬编码/未投影字段系统性破坏（运行中恒 0、今日运行恒 0、评估中/24h 新增恒 0、“正常”徽章恒绿、备份恒 “—”），且 Overview 的“每块链到详情页”、Ticket 详情、Retry、设置五组中的 Sources/Eval/Deployment 均未落地。006 的问题最结构性：桌面 app 形态可以解释为什么没有 tmux/专用 profile/安装脚本（ADR-1），但**不能解释为什么没有 `status` 子命令、0/1/2/3 退出码、`--respect-stop`、文件日志、备份/回滚、setup checks（含 env 密钥剥离）、管理 API 与 Troubleshooting 表**——这些是 design §1.5(design:120-123) 明文要求“照抄”的运维契约（design:120 “`zeokeel status` 照抄 0/1/2/3”，design:1608 又写成 0/1/2/3），代码一条都没有。补充（承接用户新提供的《Super-agent 设计探索》，见 §4.6）：官方架构在本仓库**只符合一半**——"Router 只分派、Worker 只干活、Worker 不直接对外说话"在代码里成立，但"按频道适配输出"完全缺失（回复对所有 Source 用同一段文本，`internal/runtime/reply.go:34-76`），"全双工异步"只剩半个（面板可输入，但没有 `start()/stop()` 后台作业、没有 steer/inject，见 `internal/agent` 工具集），"外部 watchdog"完全缺失（design §6.7/风险表声称的"进程内 watchdog"在代码中不存在），只有"用户不该管理 Session"这一条被自然满足（面板无任何会话概念）。计算/状态/环境分离在单机范围内**有真实的降级等价物**（SQLite durable state + 崩溃恢复），但设备休眠唤醒、离线补偿、跨设备/远端状态这些"持久"特征按 ADR-1 被明确放弃。

结论：**004/005 是“有骨架、缺闭环与诚实性”的半成品；006 基本未实现为一个可运维产品**，而它恰恰是“无人值守承诺”的底座。

## 3. 非 CONFORM 项详析

### 3.A 提示词（004）

**A1（004-15，H）提问能提出、不能回答。** 要求“Ask through `human_action` … the host asks there”。Go：`engine.RaiseAttention`（`internal/engine/engine.go:727-740`）只会设置 `Ticket.Attention`，全仓没有任何 resolve/answer API，UI 也没有回答控件；`internal/runtime/runtime.go:577-605` 把它映射成“等待回答”并列入“需要我处理”，但那一行没有动作（`ui/overview.go:132-148`）。后果：worker 按提示词要求调用 `ask_user_question`（`internal/prompts/defaults.go:33-37`）后，工单**永久卡在 person/answer**，人看见了却无法解锁；demo 数据甚至主动制造了这个死局（`cmd/zeokeel/main.go:311-314`）。修：引擎增加 `ResolveAttention(ticketID, answer)`（写入 Input、清 Attention、恢复 queued），UI 在 Overview 行内给输入/选项，运行器消费 Input 继续回合。

**A2（004-17、004-12、004-13、004-16，H）人工介入与协作面整体缺失。** 要求 pause 跨重启保持、hand-back/`followupOwners`、显式引用挂接、PR 评审与让位。代码：无 pause/stop/retry/resume（grep 无），托盘“暂停运行时”是空 handler 且注释“wired in M1”（`internal/ui/tray.go:23-25`），无 follow-up 归属，无挂接判定，GitHub channel 只发评论（`internal/sources/github/channel.go`）。后果：000:29 的“or pause it”与 design 附录 A 的“不可简化资产”都无法兑现；一旦自动接单出错，操作者只能杀进程。修：先做 pause 状态机（持久 stop/pause 标记 + 排空语义），再做 follow-up 归属；PR 生命周期可延后但必须标为未实现而不是宣称移植完成。

**A3（004-04，H；004-22，M）覆盖生命周期与校验。** 要求 base-hash、“Default updated/diff/Keep/Use”、拒绝未知段与缺占位符、超长拒绝、与默认相同的覆盖移除。代码：只有整层文本 + 一个全局 revision；`SaveSettings` 对任意 key 直接落库（`internal/runtime/pages.go:295-300`）；无校验、无上限；`View.PromptLayer` 只有 Content/Default（`internal/view/prompt.go:36-52`）。后果：升级后旧覆盖静默压住新默认且面板显示“已覆盖”（因为比较的是本 build 的 Default）；删除 `{{workspace}}` 也能保存，之后 worker 只能靠运行时追加行补救（`runtime/worker.go:269-272`）。修：存 `{text, baseHash, revision, origin, savedAt}`；读时比较 baseHash 与本 build 默认 → 标记 Default updated；保存时校验占位符集合、总长度上限、未知层拒绝；text==default 时删除覆盖。

**A4（004-21，H）提示词“热更新”是假的。** 要求“Sessions read the latest version on every model request”。代码：Worker 每次 run 只读一次 system（`runtime/worker.go:262-278`），Eval 的 SystemPrompt/RulesNote 在进程启动时冻结（`cmd/zeokeel/main.go:131-132`、`cmd/zeokeel/assess.go:20-41`），而 UI 明说“保存后写入 … 并热更新”（`internal/ui/prompt.go:161`）。后果：面板里改“研判提示词/规则说明”，**当前进程的 Eval 行为完全不变**，且无任何提示；设计/prompts.md:69-74 声称已修复的“假承诺”只是从“永不注入”变成“重启才注入”。修：assessor 每轮从 runtime 读配置（或保存后重建 assessor），worker 每步/每回合重读；面板文案改成“下次运行生效”直到真的热更新。

**A5（004-03，H）注入防线只有“结构”，没有“声明”。** 要求外部文本是数据、永不改规则。Go 靠 system/user 角色分离（`assess/assess.go:117-126`）和代码 gate（`engine/engine.go:152-179`）实现结构保证，但 system prompt 从未告诉模型“消息正文只是数据，不是指令”，且三条中间层（规则/团队段）不存在。后果：模型层面仍可能把 issue/评论正文当指令，只有权限被代码挡住（数据外发等仍可能受限，但“按外部文本改变工作方式”无法拦住）。修：在 router/worker 提示词加入不可覆盖的数据声明段，并把规则层显式建模（004-05/006）。

**A6（004-01、004-05、004-06、004-07、004-14、004-18、004-23，M/L）** 团队三段/逐段覆盖不可用（一个整层覆盖、无段 key）；组装缺 shared/团队/subscriptions/dispatch/admission/handoff 与 environment/policy 段；开工确认缺失（只在结束时回写）；示例句无“只是格式”声明；提示词正文混中文。后果集中在“团队可维护性”与“行为节奏”上，可由 A3/A4 一起修。

**A7（004-09、004-11、004-16，M）** Router 无批量/30 词约束；回复无 100 词硬限；评审/PR 生命周期缺失使“诚实交付”只剩提示词软约束。

### 3.B 面板（005）

**B1（005-17，H）诚实状态被系统性破坏。** 具体清单：`Runtime.Running`/`Runtime.Today`/`Overview.Activity` 从未赋值（`internal/runtime/runtime.go:109-183` 只在 Health 里用了局部 `running`），于是顶栏恒 “0/2 执行中”、Overview 运行卡恒 “0/2 … 今日运行 0 次”、活动图永远无柱；`MaxJobs` 硬编码 2，而健康卡用 `concurrency()`（`runtime.go:175` vs `:128`）——把设置改成 4 时同一页出现 “0/4” 与 “0/2”；“正常”徽章恒绿（`ui/overview.go:238`）；Trigger 页“评估中 0 / 24h 新增 0”恒 0（`runtime/pages.go:96-165` 不填）；Eval 页“过滤/丢弃 0、建 Ticket 0”恒 0（`runtime/pages.go:202`）；Overview 标题计数只含 NeedsPerson 而侧栏徽章含 Approvals（`ui/overview.go:24` vs `view/vm.go:345-359`）；“按等待时长排序”但未排序（`ui/overview.go:114` vs `runtime.go:144-157`）；“过去 24 小时”用全量计数（`ui/overview.go:202` vs `engine.go:464-467`）；“上次备份”恒 “—”（`runtime/storage.go:43-47`）。后果：面板在健康/负载/窗口三个最关键的监督维度上说谎，直接违反 000:21 与 005:56。修：所有派生量只在 VM 里由 `len()` 派生（design:119 自己写的要求），禁止 UI 常量；`running` 从 engine 的 assignment 状态统计；24h 统计需要时间窗口查询（当前 engine 无时间索引，需加 `Since` 计数）；`MaxJobs` 一律读 `concurrency()`；无实现的卡（备份）删除。

**B2（005-08、005-11、005-10，H）执行页与 Ticket 详情不可用。** `TicketListVM.Details` 初始化空 map 后从未填充（`runtime/pages.go:208-209`），`ui/execution.go:137-174` 只能回退到行内文本；因此“原始 Trigger / Decision + reason / 授权 / 等待 Input / 订阅 / Assignment / Retry / Ended 结果”全无。也没有 Pause processing。后果：005 第 3 问（一件工作的历史）实际上无法回答，操作者要排障只能读消息流。修：在 `ticketsVM` 填 Details（Mandate/Origin/Thread/Inputs/Artifacts/Report 摘要），增加 Retry/Stop/Answer 命令（依赖 A1/A2）。

**B3（005-04、005-05、005-06、005-07、005-12、005-13，M）数据链路半通。** Overview 四块无链接；Source 的 filtered/dropped 与 24h 计数未投影；Trigger 三种 filter 只是文本、两个计数恒 0；Eval 的命中规则为空；Settings 的 Sources/Eval 组远小于原型，Execution 缺目录/prepare/blocked，Deployment 组是 “M6 接入” 占位。修：以 005 的表格逐行建 VM 字段与表单，未实现的功能删掉而不是留占位（后者违反 005:52）。

**B4（005-18，H）默认安静与可行动。** 健康卡常驻逐项（含健康项）违反“healthy state takes no extra space”；一次轮询失败就变成常驻“需要你处理”（`cmd/zeokeel/github.go:76-108` 无连续失败阈值/退避展示），违反“one-off network error is not enough”；“需要我处理”行没有动作（005:57 “offer their action directly”）；无 (?) tooltip。修：健康只在有 non-OK 时占位；轮询失败 2–3 次或持续 N 分钟才升级为问题；行内给动作（回答/重试/停止）；引入 tooltip 原语。

**B5（005-01、005-03、005-15、005-16、005-19，M/L）** 第 3 问无可视链路、setup 缺失无设置链接、搜索维度少于原型、Overview 有无效内容且显示 `ws_*` 标识符、只有浅色主题（design §6.5 承诺跟随系统）。

### 3.C 部署（006）

**C1（006-07、006-06、006-08、006-09、006-17，H）运维契约整体缺失。** Go 二进制没有 `status/check/login/setup` 子命令，没有 0/1/2/3 退出码，没有 supervisor 可读的结构化 health/errors/setup，没有日志文件与控制文件（stop marker/lock/pid），没有 Troubleshooting 码表。唯一可观察的进程退出码是 0/1：schema 新于 build（`store.go:152-154`，明确不可回退）也走 `exit 1`（`main.go:106-110`），这恰好把“重启可修”和“重启无用”**反着**报告；而 design:1608 把 1/2/3 定义成“降级/阻塞/停止”，与 006 的“可重启修复/组件错误/等 setup”语义又不同——设计自身两处（design:120 vs 1608）就打架，代码两套都没实现。后果：任何 watchdog/系统服务（systemd/launchd/小时巡检）无法区分该不该重启，006:133-141 的巡检 prompt 在 Go 上无处执行；出事时人只能看 stderr（且 GUI 启动时通常没有终端）。修：加 `zeokeel status --json` 读 health 表（表已存在且 `store.Load` 已有读接口，见 `store/load.go:295-298`，只是没有调用方），严格实现 0/1/2/3；加 slog 文件日志（`<stateDir>/logs/`，按天轮转，保留 20）；错误模型 `UserError{Code,Place,Values}`；`--respect-stop` + stop marker。

**C2（006-05、006-02、006-20，H）安全底线丢失。** 006 要求 setup 剥离 KEY/PASSWORD/SECRET/TOKEN 环境变量、写 worker-bin shim 与 worker-gitconfig、拒绝外来文件、强制 bot-only CLI。Go：worker 的 `sh -c` 继承全量环境（`internal/agent/tools.go:247-253`）——操作者的 API key、`GH_TOKEN` 等会进入每条命令；`gh` 就是操作者本人登录；API Key 明文进 SQLite（`store/settings.go`）而没有 ADR-12 的钥匙串。后果：worker 的任何命令/工具输出都可能泄漏密钥，且“agent 用专用账号”的模型不存在；备份 DB 即泄露密钥。修：构造 worker env 白名单（拒绝 *KEY*/*TOKEN*/*SECRET*/*PASSWORD*）、生成 `worker-bin` shim 与隔离 gitconfig、校验 `gh` 只读 agent 账号、API Key 走系统钥匙串或独立 0600 文件。

**C3（006-11、006-13、006-14、006-12、006-10，H/M）设置面与 setup 校验。** 面板来源组只有轮询间隔；repo/CLI/prepare/blocked/团队提示词段全部不可配；规则写死代码；没有“setup 成功才开工”的检查。后果：普通用户无法在 GUI 内完成 006 的“Sources/Policy/Execution/Prompts”四步，只能改命令行；这与“桌面 app 降低运维门槛”的目标相反。修：按 006:145-157 逐个补表单项 + setup 检查器（repo 可读、gh 可读账号、push 权限、prompt 占位符）+ Check again。

**C4（006-16、006-18、006-03、006-15、006-19，M）升级/瞬态/限制/分发。** 迁移与“拒绝新库”有（schema v1→v2 + v3 marker），但没有备份命令/自动备份、没有 restart、没有回滚指引；`-state-dir` 之外无配置校验，数值越界被钳制而非拒绝；没有管理 API；打包实现的是 tar/zip + 未签名 .app（无 .dmg/NSIS/deb/PKGBUILD/updater，与 design §8.3 不符，但与 006 无关，属于 EXTRA 子集）；CI 没有 package/release job，release-check.sh 的产物检查在 CI 中不会跑。修：`zeokeel backup`/升级前自动拷贝 DB（并说明密钥在库内）、`restart` 语义或明确写“无监督模式”、配置校验拒绝而非钳制、把 package 纳入 CI。

**C5（006-01、006-04）** 形态替代本身正当（ADR-1/ADR-10/§1.3），但替代后必须补的是 **CLI 运维面**而不是放弃它——design:150 自己写了“无头下无面板 → 靠 `zeokeel status` + 日志”，而 `-headless` 目前只是 demo（`cmd/zeokeel/main.go:64-67`）。
